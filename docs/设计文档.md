> **项目定位：** 学生代码评估工具 - AI 时代的"懂不懂自己写的东西"验证器
> **使用者：** 教师（不直接面向学生）
> **创建日期：** 2026-07-08

> **实现状态（2026-07-09 更新）：**
> - Phase 1（骨架 + exercise 迁移）：✅ 完成
> - Phase 2（`cagen code` 核心功能）：✅ 完成
> - Phase 3（batch 批量处理）：⏳ 未开始
> - Phase 4（Prompt 调优）：⏳ 持续

## 一、背景与动机

### 问题

学生大量使用 AI 辅助完成作业（代码、文档），**"交了什么"已不能反映"学会了什么"**。传统评分方式（看提交物质量）在 AI 时代失效——一份完美运行的代码，学生可能一行都没自己写过。

### 解决思路

不是禁止 AI，而是**换个评估维度**：从"评估产出物"转向"评估理解深度"。

具体做法：让 AI 分析学生提交的代码，提取其中的知识点、设计决策、可疑区域，然后**自动生成针对性的答辩问题**，供教师面谈时验证学生是否真正理解自己的提交物。

### 为什么是独立项目

- docgen 定位是**备课材料生产**（教案、授课计划），exercise 出题放这里只是历史原因
- 评估是一个**独立的教学环节**，有自己的输入（学生代码）、输出（诊断报告）、使用场景（答辩/面谈）
- 作业生成（exercise）本身就是评估的一部分，从 docgen 迁入此项目职责更清晰

## 三、核心功能：`cagen code`

### 3.1 用途

分析学生提交的代码，一次性生成**分层答辩问题 + 诊断报告**，输出一份 Markdown。

### 3.2 命令接口

```
cagen code <PATH> [OPTIONS]

参数：
  PATH                    学生代码路径（文件或目录），必填

选项：
  --context, -c TEXT      背景信息文本（可选）
                          例："第6周作业，学过 Vue Router 和 Pinia，
                          要求做一个 Todo 应用"
  --output, -o PATH       输出 MD 文件路径（可选，默认输出到终端）
  --api-key TEXT          覆盖 OPENAI_API_KEY
  --api-base TEXT         覆盖 OPENAI_BASE_URL
  --model TEXT            覆盖 ASSESSGEN_MODEL
  --temperature FLOAT     生成温度（默认 0.5）
```

### 3.3 处理流程

```
学生代码（文件/目录）
    │
    ├─ 代码读取：遍历目录，聚合所有代码文件为带路径标注的文本
    │
    ├─ LLM 调用（一次）
    │   输入：代码全文 + 背景信息（可选）
    │   要求 LLM 输出结构化 JSON：
    │   {
    │     overview: { 文件清单, 代码量, 知识点 },
    │     diagnosis: { 知识点覆盖状态, 疑点标记 },
    │     questions: { L1[], L2[], L3[] }
    │   }
    │
    ├─ JSON → Markdown 渲染
    │
    └─ 输出 MD 文件 / 终端打印
```

**关于 LLM 调用次数：** 设计为**单次调用**获取结构化 JSON，再本地渲染为 MD。好处是快、省 token、输出稳定。如果单次效果不佳，备选方案是拆成两次调用（先分析后出题），由技术实现阶段验证决定。

### 3.4 问题三层设计（核心）

提问策略是整个工具的价值所在。**不能考"是什么"，要考"为什么"和"如果改"。**

| 层级 | 名称 | 目的 | 题量 | 示例 |
|------|------|------|------|------|
| **L1** | 理解确认 | 摸底：学生读不读得懂自己写的代码 | 2-3题 | "`store/todo.js` 里 `defineStore` 做了什么？""项目整体数据流是怎样的？" |
| **L2** | 决策追问 | 核心区分：知道为什么这么写 | 2-3题 | "Todo 列表为什么用 Pinia 不用 props/emit？""axios 拦截器里为什么加 token？" |
| **L3** | 变体假设 | 验证内化：真正理解才能答 | 2-3题 | "如果把 `/about` 路由删掉会怎样？""需求改为支持优先级，你要改哪几个文件？" |

**设计原则：**
- L1 是快速筛子——连这都答不上来的，基本没学
- L2 是关键区分层——AI 代写的能背"是什么"，但答不出"为什么"
- L3 是终极验证——需要理解代码运行时行为和架构关联，背不出来
- 每题标注对应的代码位置（文件名 + 行号或函数名），方便教师指给学生看

### 3.5 背景信息（`--context`）的作用

教师传入的背景文本让 LLM 做出更精准的判断：

| 场景 | 背景文本 | 效果 |
|------|----------|------|
| 控制不超纲 | "第6周，只学了 Router 和 Pinia" | 用了 axios 拦截器 → 标记可疑 |
| 对齐作业要求 | "要求做 Todo 应用，CRUD 全覆盖" | 缺少删除功能 → 标记知识点缺失 |
| 无背景 | 不传 | 纯靠代码本身分析，判断较粗但也能用 |

### 3.6 诊断报告内容

**知识点覆盖状态：**

| 状态 | 含义 |
|------|------|
| ✅ 确认掌握 | 代码正确使用了该知识点，写法规范自然 |
| ⚠️ 存疑 | 代码用了但写法可疑（过于复杂/风格突变/超出课程范围） |
| ❌ 未体现 | 作业应该涉及但代码中完全没有 |

**疑点标记维度：**

- **风格突变** — 同一文件内编码风格不一致（变量命名、缩进、注释语言突然变化）
- **超出课程范围** — 使用了课程尚未教授的技术（需要 `--context` 才能判断）
- **过度注释** — 每行都有详尽注释，或注释语言与代码风格不符
- **异常复杂** — 简单需求用了过于高级的写法（如一个 Todo 用了完整的设计模式）
- **AI 痕迹** — 典型的 AI 生成代码特征（如过度防御性编程、不必要的类型注解等）

> 疑点标记是**参考信号**而非定罪证据，报告措辞用"建议重点关注"而非"判定为 AI 生成"。

## 四、`cagen batch` 批量处理

### 用途

一次性处理整个班级的作业目录，每个学生生成一份独立的评估报告。

### 命令接口

```
cagen batch <DIR> [OPTIONS]

参数：
  DIR                     作业根目录，每个子目录视为一个学生的提交

选项：
  --context, -c TEXT      背景信息（同 code 命令，所有学生共用）
  --output-dir, -o PATH   输出目录（默认：DIR/reports/）
  --pattern TEXT          学生目录匹配模式（默认：所有子目录）
  ...LLM 配置选项同 code
```

### 目录结构示例

```
homework/                      ← 传入 batch 的根目录
├── 张三/                      ← 每个子目录 = 一个学生
│   ├── main.js
│   ├── App.vue
│   └── ...
├── 李四/
│   └── ...
└── reports/                   ← 自动生成的输出目录
    ├── 张三_评估报告.md
    └── 李四_评估报告.md
```

### 设计要点

- 遍历子目录，每个子目录调用一次 code 流程
- 报告文件名：`{子目录名}_评估报告.md`
- 单个学生失败不影响其他学生，错误记录到日志
- 批量结束后打印汇总：成功 N 个、失败 M 个

### 与 code 命令的关系

- `exercise`：基于**教案**出**通用题库**（所有学生统一考，笔试/课堂练习用）

- 两者覆盖评估的两个维度：统一测验 + 个性验证

### `utils/code_reader.py` 设计要点

这是 code 命令的专属工具，负责把学生代码目录聚合成 LLM 可读的文本：

- **遍历目录**：递归读取所有代码文件（按扩展名过滤）
- **排除规则**：跳过 `node_modules/`、`.venv/`、`__pycache__/`、`.git/`、`dist/` 等非源码目录
- **文件大小限制**：单文件超过阈值（如 1000 行）时截断或摘要，避免 token 爆炸
- **聚合格式**：每个文件用路径标注，方便 LLM 在问题中引用具体位置

聚合后的文本示例：
```
=== main.js ===
import { createApp } from 'vue'
...

=== stores/todo.js ===
import { defineStore } from 'pinia'
...
```

## 九、LLM Prompt 设计要点

### code 命令的 System Prompt 结构

```
角色：你是一名经验丰富的高校教师，正在进行学生代码评估。

任务：分析学生提交的代码，输出一份结构化评估 JSON。

[背景信息（如有）]

要求：
1. 分析代码的知识点覆盖情况
2. 标记可疑区域（风格突变、超出范围、过度注释等）
3. 生成三层答辩问题：
   - L1 理解确认：考"代码做了什么"（摸底）
   - L2 决策追问：考"为什么这么写"（区分真假）
   - L3 变体假设：考"如果改了会怎样"（验证内化）
4. 问题必须引用具体代码位置（文件名 + 行号/函数名）
5. 问题不能是背诵题，必须是需要理解代码才能回答的

输出 JSON 结构：
{
  "overview": { ... },
  "diagnosis": { ... },
  "questions": { ... }
}
```

> 具体 prompt 内容由实现阶段细化，此处给出方向性指导。

### exercise 命令的 Prompt

保持 docgen 中 `build_exercise_prompt()` 的实现不变，原样迁移。

## 十一、开发计划建议

### Phase 1 · 骨架搭建 + exercise 迁移 ✅
- 创建 `src/assessgen/` 包结构
- 迁移共享基础设施（llm / presets / utils / renderers / schemas）
- 迁移 exercise + render + import 命令
- docgen 同步瘦身
- **验收：** `cagen exercise` 与原 `docgen exercise` 行为一致

### Phase 2 · code 命令核心功能 ✅
- 实现 `assessment/code_reader.py`（代码读取聚合，带行号+截断）
- 实现 `assessment/models.py`（pydantic 强类型模型）
- 实现 `assessment/prompts.py`（双调用 prompt 构建）
- 实现 `assessment/renderer.py`（MD 渲染）
- 实现 `assessment/runner.py`（编排：双调用+重试+软告警）
- 实现 `commands/code.py`（CLI 薄壳）
- **验收：** 单个学生代码 -> 输出完整评估报告 MD，问题质量达标
- **实际实现差异：** 采用双次 LLM 调用（先诊断后出题）而非单次；领域逻辑收入 `assessment/` 内聚子包而非扁平布局。详见 [`Phase2-code-design.md`](Phase2-code-design.md)

### Phase 3 · batch 批量处理 ⏳
- 实现 `commands/batch.py`（复用 `assessment.runner.run_assessment`）
- 错误隔离 + 汇总报告
- **验收：** 一个班级目录批量处理，输出每人一份报告

### Phase 4 · Prompt 调优（持续）
- 收集真实学生代码测试
- 迭代优化问题质量（L2/L3 问题的区分度）
- 调整诊断报告的疑点识别准确率
